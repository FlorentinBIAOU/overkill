need:
  fr: "Obtenir la date, l’auteur et ce qu’un document transporte d’autre, avant de le publier ou de l’archiver."
  en: "Get the date, the author and whatever else a document carries, before publishing it or filing it away."

scenario:
  fr: "On voit envoyer un document à un modèle en lui demandant « qui a écrit ça et quand ». Le document le dit pourtant lui-même, en clair, dans deux fichiers XML qu’il transporte : un .docx est un ZIP, et deux de ses entrées ne contiennent que cela. Le sujet de cette fiche n’est donc pas la lecture, qui est un décompactage, c’est ce que la lecture révèle — un contrat envoyé à un client porte le nom de tous ceux qui y ont touché, le modèle interne dont il est issu et le temps qu’il a pris, et rien de tout cela ne se voit à l’écran."
  en: "Sending a document to a model and asking “who wrote this and when” is a common sight. But the document says so itself, in plain text, in two XML files it carries: a .docx is a ZIP, and two of its entries hold nothing else. So this entry is not about the reading, which is an unzip, but about what the reading reveals — a contract sent to a client carries the name of everyone who touched it, the internal template it came from and how long it took, and none of that shows on screen."

verdict_rationale:
  fr: "N0, parce que le document porte ces valeurs en clair, dans deux fichiers XML nommés par une norme publiée, à l’intérieur d’un ZIP. La bibliothèque standard suffit côté Python — `zipfile` et `xml.etree` — et côté JavaScript il fallait deux paquets sans dépendance, `fflate` pour l’archive et `fast-xml-parser` qui était déjà là. Trois choses portent la fiche au-delà du décompactage. Les parties non lues sont nommées : un document dont les auteurs sont dans ses commentaires ne doit pas répondre « aucun auteur ». Seules les deux parties de métadonnées sont décompressées, et seulement sous un plafond déclaré : une entrée de ZIP peut promettre cent mégaoctets dans un kilooctet. Et un écart entre les deux langages a été fermé plutôt que subi : l’analyseur XML de JavaScript laisse « &#232; » tel quel là où celui de Python le décode, ce qui aurait fait deux auteurs différents pour le même fichier."
  en: "N0, because the document carries these values in plain text, in two XML files named by a published specification, inside a ZIP. The standard library is enough on the Python side — zipfile and xml.etree — and on the JavaScript side two dependency-free packages were needed, fflate for the archive and fast-xml-parser, which was already there. Three things carry this entry beyond the unzip. The parts not read are named: a document whose authors are in its comments must not answer “no author”. Only the two metadata parts are decompressed, and only under a declared cap: a ZIP entry can promise a hundred megabytes in a kilobyte. And one gap between the two languages was closed rather than endured: JavaScript’s XML parser leaves “&#232;” as written where Python’s decodes it, which would have made two different authors for the same file."
