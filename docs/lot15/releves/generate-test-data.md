- **Comportement du modèle** (rangs 68, 71, 72 pour « en pratique », 78, 79, 88) : les tests N3 tournent contre un double. La phrase de la docstring de `check` « Each of these failures is one this rung produces in practice » et le commentaire de `MAX_ROWS` (rang 74) sont des affirmations sur un fournisseur réel, sans source : à sourcer ou à retirer.
- **Attribution au modèle** (rangs 63, 64) : le point de rupture N3 écrit « le modèle a renommé… », « puis a donné le même nom… ». Ce que le test rejoue est écrit à la main dans le double. La charte des tests déclare fausse une telle attribution ; aucun test ne peut porter sur une provenance. Formulation suggérée au rédacteur : « quand la réponse renomme… ».
- **Faits de plateforme et raisonnements** (rangs 10, 11, 39, 43, 44, 55, 86, 87, 89) : sans comportement de code associé.
- **Déclarations** (rangs 19, 23, 24) : dépendent de l'appelant ou de l'ordre de grandeur déclaré.

## Infirmé, et ce que le code fait réellement

- **Rang 15 — le séparateur U+001F.** Le commentaire dit qu'il n'apparaît dans aucune partie de la clé. Le code ne le vérifie pas : une graine `"a\x1fb"` avec le champ `"c"` et une graine `"a"` avec le champ `"b\x1fc"` tirent exactement les mêmes nombres. Cas rare, mais la phrase affirme une garantie qui n'existe pas.
- **Rang 20 — « chaque cellule est dérivée de la graine ».** Une colonne `sequence` (identifiants, adresses du test et de l'essai) ne lit pas la graine : `order_id` et `email` sont identiques d'une graine à l'autre. C'est d'ailleurs ce qui rend le point de rupture N0 si net.
- **Rang 47 — N1 « keeps the two languages together ».** Le tri des libellés diverge entre Python (points de code) et JavaScript (unités UTF-16) dès qu'un libellé hors plan de base (emoji) côtoie un libellé entre U+E000 et U+FFFF (formes pleine chasse, usage privé). Même graine, même table, deux jeux différents. Le cas testé : `{"🍕 restauration": 1, "Ｚ": 1}`.

## Défauts de production

- **N3, client par défaut (rang 66).** Voir plus haut : `complete` n'existe pas sur `OpenAI` ; l'erreur est avalée et transformée en `GenerationUnavailable` après trois tentatives, ce qui la rend difficile à diagnostiquer. Il manque aussi le paramètre `model`.
- **N3, demande insatisfaisable (rang 85).** `count=2.5` (ou `'2'` en JavaScript) passe la garde ; `unique_field` qui ne figure pas dans `fields` fait échouer chaque vérification. Dans les deux cas, `attempts` appels facturés sont envoyés alors qu'aucune réponse ne peut convenir.
- **N1, tri à chaque cellule (rang 58).** `sorted(spec["counts"])` et la liste des effectifs sont recalculés pour chaque ligne. Pour un `GROUP BY` de quelques milliers de libellés (codes postaux, communes), le coût devient lignes × libellés × log(libellés).
- **N0, durée nulle ou négative (rang 33).** Seule contrainte impossible non refusée : erreur cryptique pour `days=0`, et pour `days<0` des dates silencieusement différentes d'un langage à l'autre.

## Remarques pour le rédacteur (ni infirmées ni défauts)

1. Le point de rupture N0 dit « le générateur n'émet qu'une seule forme d'adresse ». C'est le **schéma du test** qui n'en a qu'une : le générateur n'a pas de type adresse, et un champ `choice` dont les valeurs portent `+billing` ou une majuscule les émet (c'est le témoin). La rupture réelle : le générateur n'émet que les formes que l'auteur du schéma a pensé à écrire.
2. Le seul lien testable entre les deux langages est désormais l'exécution croisée (Python lance Node et inversement) ; les constantes `GOLDEN` recopiées restent, et chaque test vérifie que la constante de l'autre fichier est identique.
3. Rang 11 : la phrase compare les générateurs standard « depuis la même graine », or JavaScript n'en a pas qui prenne une graine. La phrase juste : `Math.random` ne prend pas de graine, et `random.seed` de Python n'a pas d'équivalent en JavaScript.
4. `true_percent` : qui recopie une probabilité (0,3) obtient moins de 1 % de vrais sans avertissement.
5. Une graine avec accents recopiée depuis un système qui décompose (NFD) ne rejoue plus le jeu.
6. Un champ sans `type` lève `KeyError` en Python et `RangeError` en JavaScript : les deux langages ne refusent pas avec la même erreur (idem pour les autres refus : `ValueError` contre `RangeError`, attendu).
7. N1 : un effectif négatif est accepté sans erreur ; une tranche de largeur inférieure à 1 (montants en euros avec centimes, par exemple `[0, 0.5]`) ne rend que sa borne basse ; une tranche de largeur nulle rend sa borne haute, contredisant « half-open ». Une `sequence` avec `start` négatif donne `-002` en Python et `00-2` en JavaScript. En JavaScript, `count=2.5` produit trois lignes, Python lève `TypeError`.
8. N3 : `strip()` / `trim()` n'ôtent pas U+200B, une valeur invisible passe pour non vide. Aucune attente entre deux tentatives : une limite de débit du fournisseur est retentée immédiatement. Aucune limite sur le nombre de champs, seule `count` est bornée avant l'appel. En Python, `OpenAI()` est construit avant la vérification de `count` : sans clé, un `count=0` lève l'erreur du kit et non `ValueError`.

## Pour la charte

- La charte demande de « vérifier contre la version publiée du kit » la forme du client par défaut, mais le double à imiter n'existe pas dans `_harness/` : chaque testeur l'écrit dans son test. Un double `FakeOpenAIClient` (Python et JS) dans le harnais éviterait vingt-cinq variantes.
- Une affirmation d'attribution au modèle (« le modèle a renommé ») ne peut pas porter de test marqué `INFIRMÉ`. La charte pourrait prévoir le statut « INFIRMÉE (sans test) » pour ce cas, ou dire explicitement que le relevé suffit.
- Une affirmation « identique dans les deux langages » ne se démontre qu'en exécutant l'autre langage : la charte pourrait l'exiger, et lister les pièges connus (tri UTF-16 contre points de code, modulo négatif, `padStart` sur un nombre négatif).
